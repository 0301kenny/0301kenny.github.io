Case 02 · Product Management · Systems Thinking

WOTA Journey Rewards：
把複雜規則變成可交付的規格

會員等級、房晚入帳、積分、兌換與庫存規則彼此牽動。把它們整理成設計、前後端與客服都能用同一套說法理解的規格。

PM

一條規則改了，會牽動 UI、API、帳本和客服說法

Journey Rewards 讓會員透過入住累積房晚與積分，用來升等或兌換禮遇。規則本身不難懂，難的是它們互相影響：

入住→房晚入帳→積分→升等→兌換與庫存

而且同一套規則要同時出現在官網、LIFF 的介面、後端 API 與帳本、QA 測試案例，以及客服 FAQ。任何一處說法不同，客人就會被不同的答案搞混。

目標

把規則整理成一份所有角色都能對照的規格，並讓例外情境在開發前就被看見，而不是上線後才被客人發現。

PM

三個關鍵決策

房晚要算付費的晚數，還是實際入住的晚數？
以有效入住晚數為基準

例如「住三付二」這類贈送的房晚也應該計入。這個決定要同步到 PRD、API、帳本、QA 與客服 FAQ，不能只改其中一處。

夜泊、點數、房晚，到底要叫什麼？
系統用語統一為「房晚」

名詞混用是最常見的誤解來源。統一後，i18n、介面、PRD 與客服說法都改用同一個詞。

規則還在變，要一次做完還是分段上線？
分段上線細節待本人補充

先上線哪些部分、為什麼這樣切分，需要補上實際的分段方式與理由。

UI / UX

每個會籍、每種餘額，都要有對應的畫面

同一個兌換頁，會因為會籍等級、積分是否足夠、品項是否有庫存、是否過期而呈現不同狀態。我把這些組合列成 UI Flow 與兌換規格，再逐一設計對應的畫面。

狀態範例

各會籍的兌換中心、積分不足、庫存不足、兌換確認、兌換成功、空狀態、已過期、規則說明與紀錄頁。前台共整理出 35 個頁面狀態，並放進 UI Spec 工具讓團隊直接檢視。

FE

規格要能直接被實作，也要能被驗證

我用 Claude Code 參與 Journey Rewards 前台頁面的調整，包含房晚規則說明、輸入欄位、提醒文字、按鈕與路由位置，並跟著 review → staging → UAT 的節點驗收。

階段AI 負責我負責
規則整理規則、比對各版文件、探索流程分支決定產品規則、判斷衝突與商業限制
規格產生 PRD 與兌換規格初稿、例外情境檢查清單確認使用者體驗與交付範圍
前台以 Claude Code 調整頁面、文字與路由審查畫面與程式、跟著節點驗收

各階段 AI 與人的實際分工待本人確認

和後端一起討論的資料模型

會員等級的來源要擴充既有的會籍資料，還是另開一張成長等級表，兩種做法各有取捨。我提出前台需要的讀取方式，與後端一起評估。最後的決定待本人補充

過程證據：AI 初稿 vs 我的修正待本人提供素材
AI 初稿AI 產生的規格初稿（WJR PRD 某一條規則）
我的修正我修正後的版本與修正原因

放一組真實的前後對照，證明 AI 產出經過人的判斷與修正。素材需去識別化。

成果
