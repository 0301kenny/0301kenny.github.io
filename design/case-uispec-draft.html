PM

要看到一個狀態的畫面，得先等後端、登入和測試資料都到位

會員中心與 Journey Rewards 的畫面會隨會籍等級、點數餘額、庫存與日期規則變化。過去要確認某個狀態長什麼樣子，必須準備對應的帳號與資料，還要等 API 和登入功能正常。

結果是設計驗收常常卡在環境問題上，很多例外狀態要到很晚才被看見。

目標

讓團隊在不登入、不打 API 的情況下，直接看到每一個會籍、每一種狀態的真實畫面，並且保證看到的就是正式頁面。

PMFE

三個關鍵決策

用截圖、Figma，還是真的元件？
選擇渲染正式頁面的真元件

截圖和設計稿會跟實際程式脫節。副本頁的 template 跟正式頁面一字不差，只把資料換成假的，看到的就是使用者會看到的。

手機版要用縮小的桌機畫面，還是真的重排？
依選定寬度重新判斷版面

把樣式裡跟寬度有關的判斷依選定寬度重新計算，1440、1280、1024、375 四種寬度都是真的重排，手機寬度會換成手機版元件。

副本跟正式頁面久了一定會不一致，怎麼辦？
用 lint 與 build 自動把關，不靠人記得

不一致時 lint 會報錯並可一鍵同步；如果工具沒移除就要上正式環境，build 會直接失敗。

UI / UX

讓不同角色都能在 10 秒內找到要看的狀態

工具本身也是一個要設計的產品。使用者是設計師、PM 與 QA，他們要的不是程式碼，而是「我想看的那個狀態在哪裡」。

資訊架構

左側分成總覽、最近修改、頁面副本、設計 Token 四區。頁面副本再依產品分成 5 組，每張卡片標示狀態名稱與是否待確認。

瀏覽方式

上方可切換 4 種寬度與繁中、簡中、EN 三種語系，搭配輔助線、以游標為中心縮放與搜尋。網址會記住目前的分組與卡片，可以直接貼給同事。

FE

用 Claude Code 實作，由我負責判斷與驗證

工具建在公司既有的 Vue / Quasar 專案裡，必須遵守原本的 lint 與程式規範。

階段AI 負責我負責
規劃整理頁面清單、狀態組合與檔案結構草案決定要做真元件副本、範圍與分組方式
實作產生副本頁、假資料與寬度重排的程式審查程式、要求符合既有規範與 lint
驗證比對副本與正式頁面的差異逐一檢查畫面、判斷是否為真正的問題

各階段 AI 與人的實際分工待本人確認

三道防線

同步檢查npm run lint
副本與正式頁不一致就報錯
一鍵同步ui-spec:sync
以正式頁為準覆蓋副本
上線防呆prod build
工具未移除時直接失敗
過程證據：AI 初稿 vs 我的修正待本人提供素材
AI 初稿Claude Code 第一版產出（副本頁程式）
我的修正我要求修改後的版本與原因

放一組真實的前後對照，證明 AI 產出經過人的判斷與修正。素材需去識別化。
